# 应用模板改造前分析计划

状态：改造前分析、隔离探针、四候选比较和独立复核已完成。交付入口为 [综合设计对照](template-effect-assessment.md)。应用代码改造尚未开始；真实数据库、中间件和新框架组合验收在实施计划中列为待执行。

1. 读取 pstack 原则并核对三个仓库的指令、版本和工作区状态。
2. Frame：建立旧模板的文档、包、页面、API、数据库、后台服务、基础设施及验证能力清单。
3. Design：将每项已实现能力和待实施设计对应到 Effect 的源码、测试和版本边界。
4. Run：通过源码追踪和隔离探针验证关键假设，比较保留现有方案、局部采用 Effect 和全面采用 Effect 的成本。
5. Audit：记录选型依据、未验证项、兼容性风险及旧模板自身的能力缺口。
6. Verify：交付逐项对照报告、推荐架构、分阶段迁移计划和验收矩阵，再进入应用代码改造。

## 本阶段完成条件

- 旧模板每份设计文档、每个 package、页面、显式 API、迁移及运维入口都能在清单中定位。
- 每项能力区分当前实现、测试证据、文档意图、后续规划，不以 README 声明代替运行证据。
- Effect 建议具有真实源码和测试依据，并标出 rc/unstable 边界。
- RBAC、会话、CSRF、数据库迁移、事务与 outbox、worker 重试及退出、存储一致性均有明确迁移决策。
- 两个参考仓库保持只读；本阶段不修改 pstack-x 运行时代码，不写已有数据库，不启动参考仓库的共享基础设施。

## 调查分工

- 身份权限、HTTP 契约和管理端。
- 数据模型、迁移、备份、存储和基础设施。
- 后台任务、部署、验证和 agent 工作流。
- Effect 核心、HTTP、Schema、Layer 和配置对照。
- Effect SQL、迁移、并发、重试、工作流和观测对照。
