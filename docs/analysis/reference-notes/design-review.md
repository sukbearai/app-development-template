# 四个架构候选独立审阅

建议以 `design-conservative.md` 为 base。保留 vinext、Zod、Drizzle 和普通 async，先交付旧能力及其故障验收。Effect 的生命周期和类型收益已有源码与进程内探针支持，但没有证据表明模板必须先引入 Effect 才能修复身份、事务或后台问题。此推荐以“比较并吸收 Effect 的价值”为前提；如果用户明确要求默认运行时必须采用 Effect，应重新按该硬约束筛选，首选 hybrid。

本审阅比较设计质量，不表示实现或验收通过。只核对候选、同目录事实报告、探针结果、清单及旧模板 `apps/web/package.json`，没有运行应用或连接基础设施。

## 评分

每项 0–3 分。3 表示职责和验收安排明确；2 表示可行但有待补全；1 表示明显退化或大幅重建；0 表示与该标准冲突。功能不退化是硬条件，不能靠其他项目分数抵消。

| conservative | 2 | 3 | 3 | 3 | 3 | 2 | 16 |
| boundaries | 2 | 3 | 3 | 2 | 3 | 3 | 16 |

- conservative 的功能扣分来自 ClickHouse 只说保留扩展说明，尚未明确保留可选 Compose 服务，以及未显式列出 schema diff 生成验收。`UnitOfWork.run` 目前只是事务回调接口，需防止演变成通用透传层。其优势是阶段与真实验收对应清楚，不叠加新的 RC 运行时成本。见 `design-conservative.md:32`、`:59`、`:70`。
- boundaries 的共享数据边界最清楚，同分时因 worker Effect 的“采用但待证明”仍未定案，排在 conservative 之后。入口漏列 `db:generate`；同时 `pnpm dev` 默认带 worker，需要明确启动哪些消费方及 disabled 行为。见 `design-boundaries.md:7`、`:26`、`:63`。
- hybrid 保留命令及 Drizzle 工具最明确，完整业务写入接口有实际深度。但“同 key 只有一次有效副作用”缺少外部接收方幂等的前提；阶段 3 同时接入 Effect、重做事务和消费者协议，失败时难以归因。验收项尚未逐阶段绑定。见 `design-hybrid.md:34`、`:43`、`:59`、`:60`。
- effect-first 的资源与事务所有权表述准确，契约也能形成单一来源。但它同时重写协议、查询、迁移工具和后台执行，新增账本接管及回退工作；功能覆盖表不是可独立退出的实施阶段。见 `design-effect-first.md:57`、`:59`、`:69`、`:84`。

## db:generate 是实际功能退化

旧模板 `apps/web/package.json:10` 明确执行 `drizzle-kit generate`，从声明式数据库 schema 生成变更 SQL，并维护迁移元数据。`data-storage.md` 的“迁移生成、应用及安全门禁”说明了 schema、SQL、journal、snapshot 与 hash 的关系。

effect-first 在 `design-effect-first.md:57` 明确移除 Drizzle 生成器，把同名命令改成编号 SQL 骨架；`:84` 也承认失去 schema diff。人工补 SQL 和迁移后结构一致测试不能恢复自动生成能力。这个候选不满足当前不退化条件，不能通过保留命令名或注明行为变化获得豁免。

保留 Drizzle 生成链，同时换查询运行时在技术上可以另行设计，但那已经修改 effect-first 的核心取舍，本轮不把它拼入 base。Effect Migrator 的执行、锁与账本也不等同于生成器，详见 `effect-data-runtime.md:36`。迁移账本切换没有必要，应拒绝。

## 吸收哪些点

保持 conservative 的执行模型和唯一 Drizzle 事务、迁移所有者，仅吸收可独立成立的约束。

1. 从 hybrid 吸收根命令完整清单，并明确 `db:generate` 继续生成 schema diff。保留 ClickHouse 可选部署配置，默认不启动；“旧版没有分析业务”不能成为删掉已有部署入口的理由。
2. 从 boundaries 吸收 `data 不导入 server、server 不导入 Web` 的依赖方向和显式 `Transaction` 参数。仓储不得绕回全局 pool；不增加第二套数据包或通用 repository 基类。
3. 从 effect-first 吸收任务状态的判别联合，以及“已持久完成凭证”和“Kafka offset 确认”分离的返回语义。这是业务结构，与 Effect SQL 无关。
4. 从 hybrid 吸收“完整业务写入”的接口尺度。跨表写入应封装真实原子规则；仅转发一个查询的 service/repository 包装不应成为强制层。

Effect 试点保留为 base 原有的后续比较项。先选一个确有并发或生命周期复杂度的服务，对照取消、资源释放、代码量和构建依赖；通过后另作采用决定。本轮不把 worker-only、全服务端和 Effect SQL 三种执行模型混合承诺。

## base 进入实现前要补齐的验收

| 阶段 | 必须可复现的退出条件 |
| --- | --- |
| 契约、身份与工具入口 | 9 页面、15 HTTP 操作和兜底路由有映射；Cookie/Bearer、撤权、伪造 logout、同源写请求结果符合合同；隔离副本修改 Drizzle schema 后生成正确 SQL/meta，未改 schema 时不产生伪迁移 |
| 数据与存储 | 空库和旧结构升级结果一致；业务、审计、outbox 任一步失败全部回滚；事务回调不得把失败 Result 当成功提交；上传各崩溃窗口可恢复，清理不能删除仍被引用对象；含账本的备份恢复后可继续迁移 |
| 后台 | 同 key 同 payload 去重、异 payload 拒绝；过期租约恢复且旧 generation 无权完成；offset 失败不重做成功副作用；毒消息持久隔离；SIGTERM 有界排空；强杀重启后恢复。外部副作用必须另有接收方幂等证明 |
| 构建与交付 | vinext 构建产物上跑登录、管理表单、上传和刷新；浏览器依赖不含数据库、服务器配置及 Layer；真实 Redis/Kafka/S3 路径有证据；Web/worker 容器启动通过；干净树 full gate 实际执行 |

这些均为待执行验收，不继承旧模板测试或 Effect 上游测试的“已通过”状态。安全管理员初始化应改种子策略及新库初始化；历史迁移不可随意改写，既有库修复需单独处理。

## 计划与决策日志核查

`docs/analysis/plan.md` 基本保持了调查与实现的界限，没有宣称集成已经通过。第 8 行“再进入应用代码改造”应理解为阶段顺序，不应当作本轮分析自动授权实现。第 12 行的完整覆盖条件，目前清单能定位文件，但仅有总数还不能证明每个入口都已有最终迁移决定；最终报告须附能力到决策、证据和验收的映射。

`decisions.tsv` 当前两条 VERIFIED 均有对应证据且限定准确。实际读取 `inventory.json` 得到 149 个文件、9 页面、15 合同操作、13 表、3 迁移；`effect-probe/result.json` 仅记录 Layer 共享释放、类型化失败 finalizer、HttpApi 生成与 200/400 进程内响应。它们不证明 vinext、数据库、Kafka、网络或浏览器集成。

日志没有记录候选取舍、身份探针、迁移文件检查及尚未验证的集成项，属于决策轨迹缺项，不是已发现的虚假结果。主报告完成前应补记真实执行的证据路径，并把本次选择记作“设计建议”，不能记作“实现验证”。统一 GPT-6 Astra 的安排不构成跨模型验证；计划没有这样宣称。

用户需要看到三个尚未解决的取舍：vinext beta 的真实框架兼容性未验证；默认是否采用 Effect 与其 RC 升级成本仍是选型；effect-first 明确牺牲迁移生成能力。当前证据足以推荐保留主链的方案，尚不足以宣称任何候选可以直接用于生产。

## 综合报告最后核查

已核对 `docs/analysis/template-effect-assessment.md`、完整能力清单与两份相同的 inventory.json。综合报告正确落实 conservative base，保留 Drizzle 差异生成及 ClickHouse 可选配置，吸收共享包边界与事务所有权；worker Effect 仍为后续试点。没有发现将规划、上游测试或进程内探针写成真实集成验收，也没有发现已实现功能被明确删除。只需补强以下三处验收表述。

1. 综合报告 `:182` 的 P1 应明确旧结构升级与失败回滚，不只验证新库建表和并发创建。补充“从旧结构升级后约束及迁移账本一致；业务、审计、outbox 任一步注入失败均不留下部分提交”。
2. `:184` 的 P3 应补“同 key 同 payload 并发只产生一次数据库业务结果；外部副作用要求接收方幂等证据；直接终止进程后重启恢复”。硬崩溃恢复是基础 worker 的退出条件，不能只在 `:186` 的 Effect 试点验收里出现；SIGTERM 正常关闭不覆盖它。
3. 旧管理员种子修复与迁移保留两处应加一句约束：“已应用历史 SQL/journal/snapshot/hash 不改写；安全初始化用于新模板基线，已有库用独立增量迁移处理。”否则 `:81` 的种子拆分建议可能被执行者理解为直接修改历史 `0001`。

以上是设计验收和迁移约束的明确化，不改变候选选择。执行日志由父线程按真实命令补齐；本次未修改综合报告或运行应用。
