## E1 版本与 Git 工作流

使用 release-please 管理版本变化、版本更新 PR、CHANGELOG、Git 标签和 GitHub Release。Git 与 `gh` 负责分支、PR 和远端状态操作。项目不自研版本计算器。

应用采用统一版本。根 `package.json` 是应用版本的权威来源，当前为 `0.1.0`。release-please 的 manifest 记录上次发行状态，由同一工具维护并检查一致性，不另设手工版本账本。Web 和 Worker 的交付标识使用同一应用版本；内部 workspace 的包版本不代表独立发行。如果需要同步包字段，由工具统一更新。

版本策略如下。

| 阶段或对象 | 规则 |
| --- | --- |
| `0.x` | 不兼容变更提升次版本，兼容的新功能和修复提升补丁版本；通过所选 release-please 版本的配置和测试落实该策略 |
| `1.0.0` 及以后 | `fix` 提升 PATCH，兼容的 `feat` 提升 MINOR，`BREAKING CHANGE` 或 `!` 提升 MAJOR |
| 文档和工具维护 | 不默认发布应用新版本；影响交付行为的变更在版本 PR 中明确处理 |
| 预发布 | 使用 `X.Y.Z-rc.N`，与正式版分开标记；预发布验证不能代替正式版本对应提交的验证 |
| Git 标签 | 使用 `vX.Y.Z`；预发布标签保留后缀；已发布标签和同名制品不可覆盖 |
| 数据库迁移 | 保留独立迁移编号和既有哈希，应用版本不替代迁移账本 |

提交沿用项目中文提交说明，保留 Conventional Commits 的类型、可选 scope 和 breaking 标记。日常功能提交不手改版本号。采用 squash merge 时，PR 标题和正文必须保留版本工具所需的提交语义。

拟新增 `release-please-config.json`、`.release-please-manifest.json` 和 `.github/workflows/release.yml`，由工具生成 `CHANGELOG.md`。实现时固定经过验证的 action 版本，先在本地 fixture 或隔离测试仓库验证，不从当前 `0.1.0` 直接推定首个正式发行版本。

核验主分支保护或 ruleset 的实际状态、必需 CI 检查名称和版本 PR 的触发路径。GitHub 设置与工作流文件分别验收。默认令牌产生的 PR、tag 或 Release 事件不保证触发其他工作流；优先使用同一工作流中的明确依赖或可复用工作流衔接。确需 GitHub App 时，单独配置最小权限，不在仓库保存令牌。

发行配置采用草稿 GitHub Release。版本 PR 合并后，流程固定合并提交 SHA，由 release-please 准备发行元数据，再通过明确的 job 依赖执行 E2。只有该 SHA 的必需检查、同批镜像验证和发布清单校验全部成功，发布 job 才将草稿转为公开发行。正式版本与预发布保持各自标记。实现时验证所选 action 版本的草稿行为，不依赖草稿事件自动触发下游。

草稿或已预先创建的 tag 仅表示版本已保留，不能作为可部署凭据。失败时保留草稿和失败证据，不公开成功发行。无源码变更的失败重试始终绑定原 SHA；修复需要新提交时使用新候选版本，不移动既有标签，也不覆盖已发布制品。

验收要求：版本 fixture 覆盖 `0.x`、稳定版、breaking、无发行变更和预发布；版本 PR 中的版本字段与 CHANGELOG 一致；发行标签绑定正确提交；重复运行不重复发行；版本 PR 能执行必需检查；注入镜像验证失败后 Release 仍为草稿，部署入口拒绝该版本；重试不能换用其他 SHA。公开发行与可部署状态由 E2 的成功证据共同约束。

## E2 可追溯应用发布

复用现有 Dockerfile 和容器行为测试。每次候选发布固定完整源码 SHA，分别构建 Web、Worker 镜像，验证后交付同批镜像。当前 `test-containers.mjs` 会在结束时删除本次镜像，需要增加明确的候选制品交接方式，保留原有普通测试的清理行为。

目标流程为固定提交、执行源码门禁、构建候选镜像、验证候选镜像、发布同批制品、生成发布清单、执行部署验收。验证后不得重新构建一份未验证镜像用于发布。跨 job 时采用保留 OCI 制品或隔离候选仓库等方式传递同批内容，并核验 image ID 与 registry digest 的对应关系；两者不是同一种标识。

`release.json` 的拟定内容包括以下字段。

| 字段组 | 内容 |
| --- | --- |
| 清单格式 | `schemaVersion`，独立于应用版本 |
| 发行身份 | 应用版本、Git tag、完整源码 SHA、创建时间、构建工具链 |
| 应用制品 | Web 与 Worker 的仓库引用、完整 digest、目标平台 |
| 验证依据 | E3 证据索引位置与哈希、CI run 标识 |
| 升级与回退 | 迁移账本标识、已验证的数据库兼容范围、恢复协议要求、允许回退的先前版本 |

发布清单记录事实，不计算版本，也不包含凭据。仅列出真实验证过的平台。制品仓库、目标平台及保留策略在实现前按项目交付环境配置，本方案不假定现有 registry 已授权。

部署入口要求完整发布清单、匹配的成功证据和已公开的对应 Release，不能仅凭 tag 或镜像存在放行。部署配置使用固定 digest。保留迁移任务先行、生产配置预检和实际业务验收。回退前核验数据库及 Kafka recovery binding、restore guard 的兼容性。已有备份恢复能力继续负责数据恢复，切换旧镜像不能代替数据恢复。不得通过改写已应用迁移来制造兼容性。

拟调整 `scripts/test-containers.mjs`，新增制品发布与清单校验脚本、生产镜像引用配置，并扩展生产部署文档。发行工作流复用 E1，不再维护另一套版本来源。

验收要求：任一必需检查失败都不能形成成功发行；清单缺失、哈希不符或源码不匹配时拒绝交付；重试不覆盖同名不同内容；实际交付镜像可追溯到容器验证记录；隔离环境验证按 digest 启动、升级和允许的回退。工作流中的逻辑通过不等于目标部署已验收。

## E3 统一验证证据

已有 `.verification`、`artifacts`、截图、trace 和源码哈希继续保留。新增索引关联这些产物，不复制所有报告为另一份数据，也不把历史成功结果用于当前变更。

索引拟包含 `schemaVersion`、唯一 `runId`、完整 Git SHA、工作树是否有变更、源码内容哈希、构建或镜像身份、运行环境、开始与结束时间。每项检查记录名称、状态、耗时和证据引用。状态明确区分 `passed`、`failed`、`not-run`、`inconclusive`。

证据引用使用可移植相对路径和必要的内容哈希。缺失、过期、源码不符或清理失败的证据不能支持通过结论。CI 保留失败与未运行项目，并上传完整证据目录。生产发布只使用干净固定提交的证据；本地检查仍可覆盖未提交和未跟踪源码，但必须记录其内容身份。

拟扩展 `scripts/pr-verify.mjs` 和各验证脚本的汇总出口，并新增小范围索引 schema 与校验工具。业务 HTTP 契约继续由 `packages/contracts` 管理，工程报告 schema 留在工程工具范围，不把 CI 字段加入业务接口。

验收要求：能从索引定位每项原始证据；失败后仍生成索引；中断和清理失败被保留；旧源码证据、缺失文件和被改写产物被拒绝；一次 CI 的源码、构建和制品身份能够闭合对应。

## E4 工程命令标准化

复用现有 Node、pnpm 与脚本入口。先为验证、启动检查和发布相关命令统一必要契约，再按实际需要覆盖其他工具。不新建通用命令框架，不改变已有危险操作的确认和预览语义。

机器模式采用 JSON，提供 `schemaVersion`、命令名称、运行标识、状态、稳定错误代码和证据位置。机器模式 stdout 仅承载协议结果，进度和诊断写入 stderr。交互模式保留适合人的说明，不强制所有命令输出同一业务数据结构。

退出状态区分成功、参数或配置错误、检查失败与中断，并在实现时固定映射和测试。内部调用使用参数数组，拒绝未知参数。必要的重复操作保持幂等。只有确实支持预览的变更命令才提供 dry-run，不能把执行后回滚称作预览。

拟调整有需要的 `scripts/*.mjs` 和 `scripts/tests`，复用现有进程、配置加载及资源所有权逻辑。共享实现只覆盖已出现的共同需求。

验收要求：JSON 可解析且不混入日志；相同错误保持稳定代码；未知参数在创建资源前失败；中断能关闭自身进程和容器；并行运行不共用输出目录；不停止他人进程，不泄漏口令、会话或数据库连接信息。

## E5 冷启动与文档检查

增加从全新检出开始的可执行验证。检查器使用隔离目录和自有资源，按 README 的实际路径安装冻结依赖、初始化配置、启动依赖、迁移、初始化管理员、启动应用并执行最小业务流程。测试凭据在本次运行中生成，不借用已有数据库或工作区环境文件。

冷启动验证同时检查 Node、pnpm、Docker、浏览器等前置依赖的缺失提示。以真实运行结果发现文档遗漏；不只检查命令是否出现在 package.json。清理只作用于本次创建的资源，证据保留在运行目录。

API 文档继续使用现有生成一致性检查。补充本地文档链接、示例路径和功能地图的对应检查。功能地图条目必须能定位真实源码和验证入口；自动检查无法证明页面交互时，保留实际浏览器流程。

拟新增冷启动验证入口，更新 README、文档索引和 `.agents/skills/verify-pstack-x/features`。完整隔离验证放在适当 CI 阶段，不把昂贵启动过程加入每次 pre-commit。

验收要求：全新检出无人工补步骤即可走完已声明路径；缺依赖给出可操作错误；未知环境变量或既有本机服务不会让检查假通过；链接与源码映射过期时失败；中断后不遗留本次服务和容器。

## E6 量化回归比较

复用 `pnpm test:capacity` 和现有 `capacity.json`。新增比较工具读取基线与候选版本报告，记录机器、运行时、目标平台、参数、数据规模、负载配置、源码版本和重复次数。使用独立检出或串行运行，避免并发构建污染结果。

比较延迟、吞吐量、错误率、内存和资源峰值时，先核验报告是否可比较。缺失数据和不同配置不得算作通过。上传成功、准入拒绝和失败的分位数分别比较，不能靠增加快速拒绝降低总体延迟来声称性能提升。

阈值根据重复测量的波动、实际目标和评审结论确定，不默认设置任意百分比。基线更新必须有独立理由和记录，不能为了让候选通过而覆盖基线。常规 CI 先保留现有正确性检查，只有测量环境足够稳定后才启用性能阻断。

拟新增容量比较脚本与 fixture 测试，扩展 [容量测量说明](capacity.md)。输出沿用 E3 的证据身份与 E4 的命令契约。

验收要求：已知退化 fixture 能被识别；配置不一致、样本不足和缺少指标给出不确定或失败结果；重复实测保留原始样本与比较规则；修改基线有可审阅 diff；本地结果不被表述为生产集群容量。

## 实施顺序与独立验收

按以下顺序推进，每一步完成后再进入依赖它的步骤。

1. E3 统一证据索引，同时确定 E4 所需的最小结果字段。
2. E1 接入 release-please，先验证版本 PR 和检查触发路径。
3. E2 连接同批镜像验证、发布清单和交付，验收升级与回退条件。
4. E4 完成相关命令接口及工具故障测试，不重写无关脚本。
5. E5 增加隔离冷启动与文档检查，接入适当 CI 阶段。
6. E6 增加报告比较，采集稳定基线后决定阻断阈值。

实施可按独立文件范围并行开展；修改同一工作流、证据 schema 或同一验证入口时由一个负责人统一集成。运行应用、构建或数据库验证的并行任务使用独立检出和独立资源。
